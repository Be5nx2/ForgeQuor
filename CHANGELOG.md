# Changelog

All notable changes to Forgequor. Format: [Keep a Changelog](https://keepachangelog.com).

## [Unreleased]

### Added
- Readable Quota bars: each vendor shows two gauges (five-hour, week) with a label, a filled bar, the percent used and the reset time apart (weekday when not today); blue normally, orange from 80% used, red when exhausted; an unknown vendor stays greyed with its age (pol-01).
- Codex Quota read on demand: the Codex Runner asks `codex app-server` for the account's rate limits (no Quota used, 15 s timeout, a failure logged and the last reading kept), so its bar is filled at startup and every 5 minutes without waiting for a Codex Step; the session-file reading after a Step stays (pol-02).
- Remove a Project with work in progress: the removal sets its mark first, then abandons each active Run through the Abandon button's own path (open pull request closed, merged one kept Merged, running Step stopped), and a code host failure stops it with the Project and mark kept (502 naming the Run and pull request); the Projects screen shows "Removal interrupted" with Retry (also after a restart, never resumed automatically) and the confirmation lists the Runs to abandon with their pull request (rm-03).
- Remove a Project without active Runs: "Remove this Project" in the Danger zone, confirmed by typing its name and showing the Runs count, archives its finished Runs on disk, deletes every Run and then the Project, and leaves the repository alone; a Project with an active Run is refused (409). `GET /api/projects/:id/removal`, `DELETE /api/projects/:id`, `Project.removingSince` (migration 029) blocks launching and promoting while set (rm-02).
- Purge Archived Runs now: "Purge Archived Runs" at the top of the Projects screen deletes every Project's Archived Runs at once, and a red Danger zone in the Project form holds "Purge its Archived Runs now"; each asks for a confirmation stating the count and is disabled ("No Archived Run") at zero. `POST /api/archived-runs/purge` (optional `projectId`), `Project.archivedRuns`, and a "Starting over" section in the README; the daily purge is unchanged (rm-01).
- Asset Gate in the Run detail pattern: the gallery shows each Asset at real size and magnified (pixel-sharp) with its Asset Checks, a Verdict and required Feedback per rejected Asset, and its version history; the Gate bar summarises ("3 Assets to judge") and sends the Verdicts ("Send 3 Verdicts", "Approve all") with the rail visible (ui-09).
- Project selector in the sidebar (All Projects plus each Project, a native select so the keyboard works): the choice is the `?project=` query parameter, kept across navigation and refresh, and narrows the Runs home (Gate cards, merge cards, All Runs), the sidebar Gate count and the Project New Run preselects; with no Project registered the Runs home leads to Projects. Open Gates now carry their `projectId` (ui-06).
- Conversation and Spec Gates in the Run detail pattern: the Griller chat shows its rounds, questions and recommended answers with the answer box and "Confirm summary" in the panel; the spec renders as a document with its Feedback field beside it; the Gate bar keeps the summary and actions (ui-08).
- Projects as the mockup: a list of Projects (each with its own URL, `/projects/:id`) beside the selected Project's form (Checks, Setup, slots, Art Direction, Skill Packs) with one Save that applies only what changed, Discard, and "+ Register Project"; the missing-tool warning banner shows above it (ui-11).
- New Run as the mockup: Workflow choice cards, subject, solo or duo review (labelled with the seats' Runners), Seats with env-locked fields shown as locked, and a "What will happen" panel listing the Steps and the Gates that will need you, with the Quota hint when both vendors are read; `?project=` preselects the Project, and launching opens the new Run (ui-10).
- Workflows, Team, Dogfood Inbox and the note popup follow the shell's design system (page head, panels, forms, chips, buttons); no behaviour change, and the popup stays fully on screen at any window height (ui-12).
- Run detail as the mockup: header (Project, Workflow, branch, pull request), a Step rail (state, Iteration, Runner; the Agents of a review as sub-Steps) with the selected Step beside it (live log with `aria-live`, output, Feedback, Run Notes, seats used), kept in the URL as `?step=`; the Gate bar stays fixed at the top while a Gate is open, and a review Gate shows remarks, each Reviewer's vote and the Consolidator's recommendation (ui-07).
- Runs home: `/` redirects to `/runs`, which pins "Waiting for you" (one card per open Gate, with its wait and an Open/Answer button) and "Waiting for your merge" above "All Runs", a table with state chip, Workflow, current Step, Iteration and start time, filtered by state pills; the separate Waiting screen and its sidebar entry are gone (ui-05).
- One live-events stream per browser tab, shared by every screen and the Quota bars (opened with the first subscriber, closed with the last; views reload what they missed on reconnection); the sidebar's Runs entry shows how many Gates wait for you, updated live (ui-04).
- Status system and shared states: one status chip (colour, glyph, label) maps every Run state, Step state, attempt, Asset, Review verdict, Gate decision and Check result to running, waiting for you, done, failed, idle or paused (`web/src/status.ts`, tested); loading, empty (with the next step) and error (with Retry) components replace the ad-hoc text on every screen (ui-03).
- App shell: every screen sits in a left sidebar (FORGE/QUOR logotype, **+ New Run**, "All Projects" placeholder, navigation with `aria-current`, **+ Note** at the bottom) with one Quota bar per vendor on top; design tokens from the UI refresh mockups, Orbitron/Inter/JetBrains Mono with system fallbacks, `:focus-visible` outlines (ui-02).
- A URL per screen: `vue-router` (history mode) replaces the tab state, so `/runs`, `/runs/:id`, `/new`, `/projects/:id`, `/workflows`, `/team` and `/inbox` survive a refresh and Back/Forward work; unknown URLs show a not-found screen; the server serves the app for client routes without shadowing `/api/*` or assets; **+ Note** takes its tab and Run from the route; ADR 0008 (ui-01).
- `/dogfood-triage` skill: reads a Dogfood Export, groups its notes by theme, proposes a roadmap item, a spec, the Icebox or dismissal per group, writes nothing until the human agrees, and ends with the note IDs to mark triaged or dismissed in the Inbox; "Dogfooding" section in `skills/README.md` (dogfood-04).
- Export selected notes: tick notes in the Inbox (or select all shown) and **Export** writes one Markdown Dogfood Export, `export_forgequor_<date>_<time>.md`, with a header and a section per target, into `docs/dogfood/` (`FORGEQUOR_DOGFOOD_FOLDER`, created when missing, git-ignored) and offers it for download; no status changes; `POST /api/dogfood-notes/export` (dogfood-03).
- Review notes in the Dogfood Inbox: an Inbox tab lists the notes newest first with status, nature and target filters and a badge counting the new ones; a note can be triaged (with an optional reference), dismissed, or brought back to new; `PUT /api/dogfood-notes/:id/status` (dogfood-02).
- Jot a Dogfood Note: a floating **+ Note** button on every tab opens a popup (nature, target pre-selected from the tab, text) and records the note with its tab, Run or Project and date; `POST` and `GET /api/dogfood-notes`; glossary entries for Dogfood Note, Inbox and Export (dogfood-01).
- `tests/acceptance/comfort.ba.ts`: M4 BA scenarios, archiving of an abandoned Run (worktree, branches, pull request, history kept), a Claude Quota reading after a Step, Workflow validation and the Team seats (m4-11).
- Seats per Run: New Run has a folded "Seats" section (filled from the Team, locked fields read-only, a non-blocking warning with the reset time beside a seat whose Runner's Quota is used up); `POST /api/runs` takes per-seat overrides validated like the Team page; a Run freezes its effective seats at its first start and keeps them after a restart; the Run detail shows each Agent Step's Runner and model (m4-07).
- An Archived Run keeps its text Run Notes in the database (copied from the worktree just before it is removed, deleted by the purge) and the Run page lists and shows them (m4-12).
- `/to-workflow` shared Skill: turns a need into a Project Workflow, reusing a close one when it exists and validating the file through `POST /api/workflows/validate`; its reference of Step types and built-in Workflows is checked against the code (m4-10).
- Startup catch-up and purge: at startup finished Runs not yet archived are archived and stray Run folders swept; Runs archived more than `FORGEQUOR_ARCHIVE_DAYS` (default 60) days ago are deleted with everything that belongs to them, at startup and every 24 hours (m4-02).
- Archive a Run when it ends: a merged, closed or abandoned Run loses its worktree and local branch (and, unmerged, its remote branch) and is marked archived, readable as before; the Runs tab hides archived Runs unless asked (m4-01).
- Skills (shared / forgequor / godot), CLAUDE.md, brand identity doc, ROADMAP and CHANGELOG.
- Glossary, ADRs 0001–0003 and the v1 milestones (M1–M4) in the roadmap.
- Scaffold (Node/TypeScript, Fastify, Vue 3, PostgreSQL via Docker Compose, `npm start`), startup checks for `git`, `gh` and `claude`, and Project registration with a Projects list in the UI (m1-01).
- Claude Runner adapter behind the Runner seam: headless `claude` per Step, progress events, success, failure or Quota exhaustion with reset time, contract tests on a fake `claude`, opt-in smoke test (m1-02).
- Runs: start a Run from the UI, get its own worktree and branch from the freshly fetched default branch, let the Developer work through the Claude Runner, and wait at the final Gate, where the human approves or abandons it; Runs list, Run detail and "Waiting for you" screens (m1-03).
- Clean-ups from the first real Run: `.env` at the repo root is read, same-named Projects show their local path in the pickers, and headless Developer sessions cannot use tools that wait for a human (m1-10).
- Pull request and Review Brief: the Developer's branch is pushed (refused with an Escalation if a commit adds Run Notes), a ready pull request is opened through `gh` with the task and a Run reference, the Review Brief is posted as a comment, and the final Gate comes after it; the PR link shows in the Run detail. Opt-in `gh` smoke test (m1-04).
- Checks: a Project's ordered Check commands are editable in the Projects screen and run in the worktree after the Developer, stopping at the first failure; a failure goes back to the Developer for up to 2 extra attempts, then opens an abandon-only Escalation with the failing Check and its output; every attempt's commands, statuses and outputs show in the Run detail (m1-05).
- Abandon a Run in any state before Merged from the Run detail (closes its pull request, keeps its branch and worktree, even while the Developer works); Approved Runs follow their pull request to Merged or Closed through polling (`FORGEQUOR_PR_POLL_SECONDS`, default 60); Merged, Closed and Abandoned Runs free their Project slot (m1-06).
- Concurrency limit and queue: each Project has a max concurrent Runs setting (default 2, editable in the Projects screen); Runs over it are Queued and start automatically, in creation order, when a Run becomes Merged, Closed or Abandoned, or the limit is raised (m1-07).
- Quota pause and resilience: a Run whose Runner's Quota is exhausted goes Paused with its reset time and restarts its current Step after it (checked with the pull request poll); after a restart, Running Runs restart their Step, Queued Runs start and Approved Runs are followed again; a Developer Step past `FORGEQUOR_STEP_TIMEOUT_MINUTES` (default 60) is killed and escalated; timed out Steps and Checks, and Runs abandoned mid-work, are killed with their whole process group (m1-08).
- Live Step progress: the Forge core publishes the running Step's events and every Run change, served as server-sent events, so the Run detail shows what the Agent is doing as it happens and the Run screens update without polling or a reload (m1-09).
- Dogfooding readiness: a Project declares ordered setup commands (editable on the Projects screen) that run in each new worktree before the Developer, and a failing one opens an Escalation with its output; the Docker Compose project has a fixed name so Run worktrees share the one PostgreSQL; the README shows how to register Forgequor itself (m1-11).
- Workflows out of the core: the M1 sequence (setup, Developer, Checks, pull request, final Gate) moves into the `developer` Workflow behind an internal Workflow interface, while the Forge core keeps the Run lifecycle; every Run carries its Workflow name (existing Runs are `developer` Runs), shown in the Runs list and the Run detail (m2-01).
- Reject a `developer` Run with Feedback: the final Gate offers approve, reject (with a required written Feedback) or abandon; rejecting starts a new Iteration where the Developer works again in the same worktree with the task and every Feedback so far, the Checks run again with a fresh retry budget, new commits go to the same pull request with a new Review Brief comment, and the final Gate reopens; the Run detail lists the Iterations (m2-02).
- Codex Runner adapter behind the Runner seam: `codex exec` headless with JSON events, sandboxed to the worktree with approvals off (ADR 0006), the Agent's instructions and model passed through, one fresh session per Step, cancellable like the Claude Runner; a succeeded Step returns the images Codex generated, collected by thread from `CODEX_HOME`; usage limits become Quota exhausted (with the reset time when Codex gives one); startup checks `codex`; contract tests on a fake `codex` and opt-in `npm run smoke:codex` (m2-03).
- First `assets` Run: pick the Workflow and list Asset Requests (sprite or tile, size) in the Run form; the Artist (Codex) draws each Asset in turn at its target path under the Project's art folder, after a missing Art Direction opens an Escalation; the Asset Gate shows each Asset at real size and magnified with crisp pixels on a changeable background, and approving it commits the Assets, opens the pull request with a Review Brief Forgequor writes, and approves the Run. A Runner and model per Agent, Project art settings, an image route that serves only recorded PNGs, and 400 (not 409) for a Gate decision refused for bad input (m2-04).
- Asset Checks: each Asset is validated as a readable PNG with an alpha channel, of the exact size, at its target path (pure-JavaScript `pngjs`); a failing Asset goes back to the Artist with the reason for 2 extra attempts, then an Escalation names it; nothing written gets one more try, then an Escalation with the Artist's last message; a fill flag on Asset Requests (the Artist fills the whole square and any transparent pixel fails the checks); hostile files are refused before decoding; colours outside the Art Direction's `Palette` codes show as a warning on the Asset; `npm run smoke:codex` now checks the file the Artist wrote a decided Asset Gate no longer says Assets are waiting, and the Projects screen's Art Direction field shows its whole path (m2-05).
- Per-Asset verdicts: the Asset Gate takes a verdict for every waiting Asset at once (approve, or reject with its own Feedback; a partial set or an empty Feedback is refused with 400); the next Iteration redoes only the rejected Assets with their Feedback and the rejected version kept in the Run Notes as a reference, approved Assets are kept, there is no limit on Iterations; the gallery shows each Asset's past versions and Feedback, and the Review Brief lists the Feedback behind each Asset (m2-06).
- Animation Strips: an Asset Request can be an animation with a frame count (at least 2); the Artist lays the frames side by side in one image, it lands in the `animations` folder, the Asset Checks expect a width of frame width × frame count, the gallery shows the strip with its frame count, the Review Brief gives it, and past versions of an Asset are shown magnified like the current one (m2-07).
- References, default size and safe replacement: the reference images an Art Direction names are always attached to the Artist (Codex takes them as images), and an Asset Request can name more; a `Default size: WxH` line presets the Run form's size; an Asset Request can replace an existing file (the old art becomes a reference); starting a Run is refused when a file would be overwritten without that mark, two requests would produce the same file, or a reference does not exist; the Art Direction contract is documented in the README (m2-08).
- Resilient, live `assets` Runs: an exhausted Codex Quota pauses the Run and resumes it at the Asset it was on, a restart picks up at the current Asset keeping those already drawn, abandoning kills the running Artist, and the Run detail shows progress Asset by Asset; live progress events now carry a numeric Step attempt id (the Run page's live list never matched before); a decision at a Gate racing an abandon can no longer deadlock the database (Run row locked before Gate row); tests cover resuming a `developer` Run in the middle of a Feedback Iteration after a Quota pause and after a restart, and a rejection racing an abandon (m2-09).
- Launch checks on fresh repository state: starting an `assets` Run (and the Run form's art facts) fetches the default branch first, a replacement's commit and Review Brief say it replaces, and the Asset Gate shows the replaced art beside the new version (m2-10).
- Overwrite check when an `assets` Run really starts: after its worktree is made from the freshly fetched default branch, an Asset not marked as replacing whose target path already holds a file opens an Escalation naming it before anything is generated, so a Run that waited in the queue cannot overwrite art merged meanwhile (m2-11).
- Approved Runs free their slot: an Approved Run no longer counts against its Project's concurrency limit and becoming Approved starts the next Queued Run; "Waiting for you" gains a "Waiting for your merge" list of every Approved Run with its pull-request link; the Runs list names same-named Projects by path, ignores out-of-order loads and says when it is loading or failed (m3-00a).
- Workflow definitions: a Workflow's YAML (name, description, launch inputs, Steps of type `agent`, `checks`, `gate` `final` or `asset`, `publish` or `artist`, with `needs`, `readonly`, `on_reject`, `max_attempts` defaulting to 3 and `when`) becomes a validated definition, or every error at once with its path, line and column (duplicate or unknown ids, unknown types, Agents or Gate kinds, a `needs` cycle, Steps that can run together without both being read-only, an `on_reject` target not before the Step, a `when` input neither given at launch nor produced by a Step it needs); the built-in `developer` and `assets` Workflows ship as YAML describing today's behaviour; pure-JavaScript `yaml` parser added; not yet used by the engine (m3-03).
- M2 review follow-ups: an `assets` Review Brief lists each Asset's palette warnings; every Gate records its Iteration (earlier Gates get theirs at migration) and an Asset Gate's verdict Feedback shows as the Feedback of the Iteration it started; a read Run exposes each Artist attempt with its Asset Check failures, listed in the gallery; the Replaced Art stays a Style Reference in every Iteration; one cap of 3 Artist Steps per Asset per Iteration (2 when nothing is written twice) replaces the two budgets that added up to 4; a bare Codex `error` event on an unfinished turn is a failure, never an exhausted Quota; the UI types its API with the server's own shapes (gaining the `rejected` Asset status) and loses a dead "Approve all Assets" label; tests abandon Runs through the Forge; the README's art path lists `animations` (m3-00b).
- One Agent Step executor: how a Step's result becomes progress, an Escalation (failure or timeout) or a Pause (Quota) is written once for both Workflows, and a Workflow's context no longer holds the database pool but the Run's own records and a publish operation; nothing visible changes (m3-01).
- Assets out of the core: each Gate kind (final, asset, escalation) is a module that offers its choices, validates a decision and says where the Run goes next; a Workflow declares its launch inputs and its Step types validate and store them inside the launch transaction; Asset Requests, rows, verdicts and images live behind the `artist` Step type and `asset` Gate kind, so the Forge core imports no Asset code; nothing visible changes (m3-02).
- The Workflow engine runs `developer` from its YAML: a Run stores the definition and inputs it started with (Runs from before get their built-in definition at migration); Steps start when what they need is done or skipped; `when` is checked when a Step is ready, on launch inputs and inputs earlier Agent Steps produced (an invalid produced input goes back to its Step); a Check that fails loops back to its `on_reject` Step and replays what follows, an Escalation opening after `max_attempts` (3), while Gate rejections start a new Iteration with no cap; each Step's state and attempts are kept per Iteration and listed in order in the Run detail; a restart or resume starts again only the Steps that were running; `assets` still runs as code (m3-04).
- The Workflow engine runs `assets` from its YAML too: `artist` (a coded Step type drawing each Asset Request in turn with its Asset Checks and retries), the asset Gate (rejected Assets go back to `artist`, a replayed Gate ignores older decisions), then `publish` (commit and Forgequor-written Review Brief), the Run being Approved after Publish; the Run detail lists the Steps of `assets` Runs, and no Workflow runs as code any more (m3-05).
- Parallel read-only Steps: the Workflow engine starts ready read-only Steps together and settles the batch as a whole (one Gate, Escalation or Pause per batch, first in definition order; a rejection never resets a running sibling); a read-only Step that changed anything outside the Run Notes fails with an Escalation naming the files; a Run still holds one slot (m3-06).
- Project Workflows: a game brings its own Workflows in `forgequor/workflows/*.yaml`, read from its freshly fetched default branch when the Run form loads and at launch; one named like a built-in replaces it, an invalid one is listed with its errors and refused at launch, and the Run form builds itself from the chosen Workflow's launch inputs (m3-07).
- Escalations with choices: the human can retry the Step that failed (optional Feedback, fresh attempt budget), go back to an earlier done Step (required Feedback; it and every later Step replay in the same Iteration, files not reverted) or abandon; the Feedback reaches replayed Agents like Gate Feedback (m3-08).
- Display fixes from the M3a acceptance run: Steps of Runs from before M3a read done once approved, merged or closed; no Step of an abandoned Run stays running; Run detail Steps no longer run their type and detail together; "1 attempt" is singular; the Run form shows "Loading Workflows…" and disables Start Run until a Workflow is selected; the Runs filters wrap instead of overflowing.
- A dedicated "New Run" tab between "Waiting for you" and "Runs": the Run form leaves the Runs screen, which now shows only the history, and a launched Run opens its detail.
- Shared Skill Pack placed in every Run's worktree for Claude and Codex, never committed, the Project's own Skills winning (m3-10).
- `bugfix` Workflow with a solo Reviewer: a bug description goes to the Developer (failing test first, `diagnosing-bugs`), the Checks, a read-only Reviewer whose Review ends in pass or changes requested (changes loop back to the Developer up to `max_attempts`, then an Escalation), the pull request with the Review in its Review Brief, and the final Gate; one Runner and model seat per Agent (`FORGEQUOR_<SEAT>_RUNNER` / `_MODEL`); a solo or duo review choice in the Run form (duo reviews solo until m3-12); Reviews readable in the Run detail (m3-11).
- Duo review: Reviewer A (Claude) and Reviewer B (Codex, read-only sandbox) review side by side, then the Consolidator checks each remark against the code and writes the one Review; an unsettled disagreement opens a review Gate with its recommendation (approve, reject with Feedback, abandon); one Escalation or Pause when both Reviewers fail, and readable Escalation wording for Reviewers (m3-12).
- `feature` v0: the Griller grills a free-text subject in a Conversation Gate (one round of questions at a time, answered in a chat in the Run detail, one Claude session resumed each turn, transcript in `.forgequor/grilling.md`, restart-safe), changes only `GLOSSARY.md` and `docs/adr/` (committed on confirm), then the Developer builds from the subject and the confirmed summary, Checks, duo review, pull request and final Gate; an Escalation can go back to the Griller to reopen the conversation (m3-13).
- Art inside `feature`: the Griller writes Asset Requests in a Run Note, validated on confirm like `assets` launch input (invalid ones reopen the conversation with the reasons); the Artist and the Asset Gate then run only when art was ordered, approved Assets are committed, and the Developer is given their paths; the pull request still opens once, at the end (m3-16).
- Architect in `feature`: after the spec Gate, the Architect reads the spec and the code and writes an Implementation Plan to the Run Notes (`implementation-plan.md`: modules, test seams, order of small steps; a missing or empty plan is a failed attempt), may add Project ADRs under `docs/adr/` (Forgequor commits them; any other change is swept and escalated), and no Gate follows; the Developer is given the plan.
- Spec Writer and spec Gate in `feature`: after the Griller, the Spec Writer turns the grilling (transcript and confirmed summary) into `docs/specs/<slug>.md` with `to-spec`, asking nothing and writing no tickets; only that file may change, and it is committed in the pull request (an existing spec at that path escalates instead of being overwritten). The human reads it rendered at a spec Gate and approves it or rejects it with Feedback to have it redone; the Developer is given the spec's path and the Reviewers review against it. Specs, the Griller's questions and its summary are shown as safe rendered Markdown in the Run detail and "Waiting for you" (m3-14).
- Claude Quota bar: a Quota Reading (five-hour and weekly percent used and reset time, exhausted or not) is read from Claude Code's `/usage`, which costs no Quota, at startup, after every Claude Step and every 5 minutes, and partly from each Step's rate limit events; Forge core stores the latest reading per vendor, pushes it on the live-events stream and serves `GET /api/quota`; a compact bar per vendor tops every tab, greyed "unknown" without a reading (Codex's fills in with m4-05) (m4-04).
- Workflows tab and validation (m4-09): `GET /api/projects/:id/workflows` also gives each Workflow its Steps, YAML and whether it replaces a built-in one; `POST /api/workflows/validate` checks YAML text as launch does and stores nothing; the Run form offers only valid Workflows and the new read-only Workflows tab shows why one is not.
- Codex Quota bar and Quota pauses: after each Step the Codex Runner reads the last `token_count` rate limits of the thread's session file (`primary` five-hour, `secondary` weekly; none when the file is missing or unreadable), and a Quota pause on any Runner records an exhausted reading with its reset time so the bar agrees with the pause (m4-05).
- macOS notifications: a Notifier port in Forge core (`osascript` in production, silent with `FORGEQUOR_NOTIFICATIONS=off`) tells the human when a Run waits at a Gate, opens an Escalation, pauses on an exhausted Quota, or has its pull request merged or closed, naming `Run #id "Title"`; a failing notification never touches a Run (m4-03).
- Team page: each seat's Runner and model are set in the app and saved in the database (environment variable first, then Team setting, then default; a locked field is read-only and names its variable), seats are read when a Run starts so a change needs no restart; `GET /api/team`, `PUT /api/team/:seat` (m4-06).
- Skill Packs per Project: a Project's page lets the human pick the Skill Packs Forgequor ships (besides `shared` and `forgequor`); a Run places `shared` then the chosen packs for Claude and Codex at its first start, never committed, a Project's own Skill winning (m4-08).
